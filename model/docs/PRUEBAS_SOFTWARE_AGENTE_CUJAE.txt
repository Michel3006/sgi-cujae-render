1. OBJETIVO Y ALCANCE DE LAS PRUEBAS
--------------------------------------------------------------------------------

Este documento describe las pruebas realizadas sobre el backend del agente que
responde preguntas sobre la producción científica de la CUJAE. El alcance cubre:

  - Módulos críticos de seguridad SQL y parsing de respuestas del LLM.
  - Reglas de dominio en prompts (CUJAE, sinónimos, búsqueda fuzzy).
  - Contrato REST del API (caja negra) con dependencias externas simuladas.

Quedan fuera de la automatización (pero se recomiendan como pruebas manuales de
integración en la tesis):

  - LM Studio real con un modelo concreto y GPU.
  - PostgreSQL institucional con datos de producción o copia anonimizada.
  - Pruebas de usabilidad con usuarios del sistema de gestión.

4. DETALLE DE PRUEBAS DE CAJA BLANCA
--------------------------------------------------------------------------------

4.1. Módulo sql_fuzzy — Normalización de búsqueda por similitud
---------------------------------------------------------------
OBJETIVO: Garantizar que filtros por nombres/títulos no usen igualdad exacta,
problema frecuente cuando el usuario escribe mal un nombre o solo el apellido.

CB01.1  test_equality_becomes_ilike_single_token
  Entrada:  SELECT ... WHERE i.name = 'Garcia'
  Esperado: Sustitución por LOWER(i.name) ILIKE '%garcia%'
  Justificación: Valida la regla de negocio “búsqueda por fragmentos”.

CB01.2  test_equality_multiword_uses_and
  Entrada:  f.fullname = 'Maria Lopez'
  Esperado: Dos ILIKE unidos con AND (%maria% y %lopez%)
  Justificación: Nombres compuestos deben coincidir en todas las partes.

CB01.3  test_numeric_equality_unchanged
  Entrada:  p.id_faculty = 3
  Esperado: SQL idéntico (sin ILIKE)
  Justificación: IDs numéricos deben seguir siendo comparación exacta.

CB01.4  test_ilike_without_wildcards_gets_tokens
  Entrada:  a.title ILIKE 'Redes neuronales' (sin %)
  Esperado: Tokenización en %redes% y %neuronales%
  Justificación: El LLM a veces omite comodines; el backend los corrige.

4.2. Módulo sql_guard — Seguridad de consultas
-----------------------------------------------
OBJETIVO: El agente solo puede ejecutar SELECT acotados; evita inyección o
destructores si el modelo alucina SQL malicioso.

CB02.1  test_rejects_empty_sql
  Esperado: ValueError “SQL vacío”
  Justificación: Entrada inválida no debe llegar a PostgreSQL.

CB02.2  test_rejects_sql_comments
  Entrada:  SELECT con comentario --
  Justificación: Comentarios pueden ocultar código en ataques de inyección.

CB02.3  test_rejects_multiple_statements
  Entrada:  SELECT ...; DELETE ...
  Justificación: Una sola sentencia por petición del chatbot.

CB02.4  test_rejects_non_select
  Entrada:  DELETE FROM integrant
  Justificación: Política de solo lectura a nivel aplicación.

CB02.5  test_rejects_forbidden_keywords
  Entrada:  SELECT DROP TABLE integrant
  Justificación: Palabras reservadas destructivas aunque empiecen por SELECT.

CB02.6  test_appends_limit_when_missing
  Esperado: Añade LIMIT según SQL_MAX_ROWS
  Justificación: Evita respuestas enormes y sobrecarga del LLM en 2.ª pasada.

CB02.7  test_caps_limit_when_exceeds_max
  Entrada:  LIMIT 500 con máximo configurado 50
  Justificación: El tope institucional prevalece sobre el del modelo.

CB02.8  test_applies_fuzzy_on_name_equality
  Integración guard + fuzzy en un mismo flujo de validación.

4.3. Módulo sql_llm — Interpretación de respuestas del modelo
-------------------------------------------------------------
OBJETIVO: El primer paso del agente exige JSON estructurado; este módulo debe
ser tolerante a formatos alternativos sin aceptar basura.

CB03.1  test_parse_json_with_sql
  Entrada:  {"sql":"SELECT 1","direct_answer":null}
  Justificación: Camino feliz text-to-SQL.

CB03.2  test_parse_json_direct_answer_only
  Entrada:  sql null + direct_answer (saludo / fuera de alcance)
  Justificación: No toda interacción requiere base de datos.

CB03.3  test_parse_markdown_sql_fence
  Entrada:  Bloque ```sql ... ```
  Justificación: Algunos modelos ignoran JSON y usan markdown.

CB03.4  test_prefers_sql_when_both_sql_and_direct_answer
  Justificación: Si hay SELECT válido, prevalece consulta sobre texto libre.

CB03.5  test_invalid_response_raises
  Justificación: Error controlado → HTTP 400 en el router.

CB03.6  test_extract_sql_from_llm_response
  Justificación: API auxiliar para flujos que solo necesitan SQL.

CB03.7  test_extract_sql_fails_on_direct_answer
  Justificación: Evita ejecutar BD cuando la respuesta es conversacional.

4.4. Módulo ask_data_prompts — Reglas de dominio CUJAE
-------------------------------------------------------
OBJETIVO: Verificar que los prompts contienen las restricciones que reducen
alucinaciones (institución, sinónimos, ILIKE).

CB04.1  test_domain_context_mentions_cujae
CB04.2  test_synonym_glossary_maps_integrant
CB04.3  test_fuzzy_rules_forbid_exact_equality
CB04.4  test_sql_system_prompt_includes_schema_and_limits
CB04.5  test_answer_prompt_mentions_cujae_and_no_hallucination

  Justificación global: Los prompts son “código ejecutado por el LLM”; si faltan
  reglas, el comportamiento del agente degrada aunque el código Python sea correcto.

8. LIMITACIONES CONOCIDAS DE LA ESTRATEGIA DE PRUEBA
--------------------------------------------------------------------------------

  1. Los mocks no garantizan que un modelo real siempre genere JSON válido.
  2. _FakePool no reproduce todos los tipos de asyncpg.Record (suficiente para
     pruebas de conteo y serialización básica).
  3. No se mide latencia ni consumo de tokens (pruebas no funcionales futuras).
  4. sql_guard puede rechazar SELECT legítimos que contengan palabras como
     DELETE dentro de cadenas literales — trade-off seguridad/falsos positivos.
